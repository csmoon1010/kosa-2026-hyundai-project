# Scenario IR: 독립 체크박스 기반 컨텍스트 압축 작업계획서

작성일: 2026-11-01
상태: 독립 체크박스·두 압축 구현 및 8가지 조합의 자동 검증 반영. 실제 검색의 k=1~10 비교 완료. 실제 모델 24회 반복 평가는 자동 승인 검토에서 차단되어 미실행. 기본 k=5 유지. 상세 결과는 `scenario_ir_context_compression_verification.md` 참조.

기준 문서: `scenario_ir_agent_plan.md`, `scenario_ir_validation_retry_plan.md`

## 1. 목표와 범위

현재 기본 동작과 정지·재시도 정책을 유지하면서 아래 세 기능을 UI의 독립 체크박스로 선택한다. 세 기능은 서로를 자동으로 켜거나 끄지 않으며, 모두 선택한 경우를 포함한 8가지 조합을 지원한다.

- 중지조건·재시도: 기존 `validated` 정책을 적용한다.
- 압축 1: 선택된 API 안에서 조건, original_question, 현재 STEP selection_reason의 세 검색 질의를 사용한다. 조건 질의에는 명확하거나 LLM이 관련 있다고 판정한 다른 STEP 조건만 문맥으로 합친다. 별도 관련 STEP 질의를 늘리지는 않는다. 각 질의는 top-k=5로 시작하고 후보의 상세 근거만 모델에 전달한다. 동일 질의는 출처 라벨을 합치고, 후보 경로는 중복 제거한다.
- 압축 2: 백엔드가 의존성을 기준으로 선행 STEP의 식별자·필요 출력 정의와 후속 STEP의 관련 조건·소비 관계만 모델에 전달한다.

의도분석에서 검색할 조건과 값이 이미 구조화되었다고 가정한다. 조건 분리 전용 LLM 호출은 추가하지 않는다. 오래된 대화의 LLM 요약, 매 턴 이력 압축, Baseline·Response Outputs 자체의 검색 압축, STEP 간 조회 캐시는 이번 범위에서 제외한다.

고정된 STEP·API, Structured Outputs, Baseline 백엔드 비교, 출력 보완, IR 저장·미리보기·JSONL 로그를 유지한다. 필수 여부 판단, Assertion 생성, 실제 업무 API 실행, 사용자 질문 흐름은 추가하지 않는다. 저장 상태는 기존 `needs_input` 분석용 초안이다.

## 3. UI·API 옵션 계약과 호환성

### 3.1 UI 동작

기존 생성 모드 select를 체크박스로 교체한다.

```text
생성 옵션
☐ 중지조건·재시도
☐ 압축 1 · 조건별 ParameterKB 검색
☐ 압축 2 · 의존성 기반 STEP 문맥 선별
```

- 초기값과 기본값 복원은 모두 해제다. 모두 해제하면 현재 기본 모드와 같다.
- 기존 숫자 예산 4개는 유지한다. 어떤 조합에서도 호출·토큰·시간 예산이 적용된다.
- 승인 직후 자동 생성과 승인본 재생성에 같은 옵션 전달 경로를 사용한다.
- 생성 시작 시 선택값을 복사하고 완료·실패까지 체크박스와 기본값 복원을 잠근다. 승인본 목록 갱신으로 선택값이 초기화되지 않게 한다.
- 진행·실패·저장 결과에는 실제 실행한 옵션 조합을 표시한다. 이전 결과를 볼 때 현재 체크 상태로 실행 옵션을 추정하지 않는다.

### 3.2 API 계약

숫자 설정과 독립적으로 아래 객체를 전달한다.

```json
{
  "generation_options": {
    "stop_retry": true,
    "kb_rag": true,
    "dependency_projection": true
  }
}
```

- 새 객체의 생략된 키는 false다. boolean만 허용하고 알 수 없는 키·객체가 아닌 값은 거부한다.
- 새 옵션과 기존 모드가 모두 생략되면 모두 false다.
- 기존 `generation_mode=basic`은 모두 false로, `validated`는 `stop_retry=true`와 두 압축 false로 변환한다.
- 두 형식이 함께 전달되면 기존 모드가 뜻하는 `stop_retry` 값과 새 옵션의 값이 일치할 때만 허용한다. 압축 선택은 새 옵션을 따른다. 충돌은 명확한 요청 오류로 처리한다.
- `generation.config`의 숫자 4개 구조는 유지하고 정규화된 옵션은 `generation.options`에 별도 저장한다.
- 기존 `generation.execution_mode`는 `stop_retry`에 따라 basic/validated를 유지한다. 압축 여부는 이 문자열로 판별하지 않는다. 기존 IR에 options가 없으면 execution_mode를 기준으로 호환 표시한다.
- `generation.policy`, 검증 실행 상태, 시작 이벤트에도 실제 적용된 정책·옵션을 기록한다.
- 일반 JSON 응답과 NDJSON 스트리밍에 동일한 정규화 함수를 적용한다. 생성 시작 후 정책은 변경하지 않는다.

### 3.3 중지조건·재시도 의미

기존 validated 정책의 범위를 변경하지 않는다. 선택했을 때만 inputs·outputs·bindings 매핑 검증, 저장 전 동일 범위 검사, 일시 통신 오류 추가 1회, STEP 매핑 수정 최대 1회를 적용한다. 자료 조회는 수정 횟수를 초기화하거나 소비하지 않는다. 검증 후 확인용 LLM 호출은 추가하지 않는다.

해제해도 현재 기본 모드의 파싱·자료 확보 확인·오류 처리와 전체 예산은 유지한다. 체크 해제를 모든 정지 조건 제거로 해석하지 않는다. 코드의 `mode == validated` 직접 비교는 옵션에서 도출한 정책을 사용하도록 점검한다.

## 4. 압축 1: API 범위의 조건별 ParameterKB RAG

### 4.1 입력 전제와 기존 파일

구조화 조건은 조건 ID, 검색 의미, 원래 값·단위, 원문 근거 위치를 제공하는 내부 형식으로 정규화한다. 값 자체를 검색어로만 사용하지 않는다. 예를 들어 상품 가격을 검색하고 50000원은 매핑할 값으로 보존한다. 판매가인지 공급가인지 불명확한 의미를 전처리에서 확정하지 않는다.

현재 예시의 `intent_task.conditions`는 문자열이다. 원본을 덮어쓰지 않고 어댑터를 둔다. 구조화 조건이 있으면 재사용하고, 문자열만 있으면 조건 전체를 단일 질의로 사용한다. 조건이 비어 있거나 검색에 충분하지 않으면 해당 API의 전체 KB 조회로 전환하고 그 이유를 기록한다. 기존 의존성 코드가 문자열 정규식을 적용하는 부분도 자료형에 맞게 처리한다.

### 4.2 검색과 상세 자료 전달

1. 승인된 `selected_api_id`로 검색 대상을 먼저 제한한다. 전체 API 검색 후 사후 필터링하지 않는다.
2. 검색 질의는 현재 STEP 조건, original_question, 승인 자료의 현재 STEP selection_reason 세 범주로 구성한다. 조건이 문자열이면 단일 조건 질의, 이미 구조화되어 있으면 각 구조화 조건에 질의를 만든다. 조건 분리 전용 LLM 호출은 추가하지 않는다.
3. input_dependencies/output_consumers로 관련 STEP이 명확하면 승인된 관계를 우선 사용한다. 관계가 없거나 ambiguous인 경우 첫 KB 도구 호출의 같은 LLM 턴에 다른 STEP의 ID·업무·조건(API ID 포함 최소 요약)을 제공하고, LLM은 관련 STEP ID·0~1 점수·짧은 근거만 반환한다. 별도 분류 호출이나 연결 검색문 생성은 추가하지 않는다. 초기 임계값은 0.7로 두며 검증 데이터로 조정할 수 있도록 로그에 점수·선정 상태·임계값을 남긴다. 백엔드는 후보 목록 밖 ID, 현재 STEP ID, 중복 ID, 범위 밖 점수, 근거 없는 판정을 거부한다. 모호한 dependency가 있으면 승인 candidate_source_step_ids 안에서만 판정한다.
4. 선택된 STEP의 실제 업무 조건만 현재 조건 질의에 문맥으로 합친다. 같은 업무·같은 조건을 가진 복수 STEP은 검색문에서 한 번만 표현한다. 후보 STEP의 관련도 점수/판정 근거를 ParameterKB 필드 근거로 사용하지 않는다. 선택된 STEP 조건만 추가하며 다른 STEP 조건을 단독 질의로 검색하지 않는다.
5. 파라미터 단위로 의미·별칭·설명과 사용할 수 있는 검증 지식을 인덱싱한다. 파라미터 경로, 원본 배열 위치, 출처를 메타데이터로 유지한다.
6. 세 검색 범주(구조화 조건은 조건별)의 임베딩 검색을 top-k=5로 수행한다. 검색 임베딩은 API별 요청에 묶어 호출하되, 결과 출처와 선택된 관련 STEP을 각각 기록한다.
7. 후보를 합치고 전체 parameter_path 기준으로 중복을 제거한다. 정확 경로·별칭 일치는 유사도 순위만으로 제거하지 않는다.
8. 후보의 identity·knowledge·schema·schema_sources와 필요한 provenance 및 적용 범위가 맞는 VERIFIED 공통/API 규칙을 가져온다. 선택된 후보에 필요한 연관 필드·규칙도 포함한다.
9. 검색 점수나 인덱스 텍스트를 근거로 삼지 않고, 기존 JSON에서 읽은 상세 원문을 LLM에 전달한다.

KB 우선 조회 원칙은 유지한다. 압축 1이 꺼져 있으면 기존 전체 KB 반환·도구 인자 계약을 그대로 사용한다. 켜져 있으면 백엔드가 현재 조건을 조회 문맥으로 제공하고, KB 도구가 그 문맥으로 검색한다. 모델 도구 이름은 기존 3개를 유지하는 방향으로 구현하며, 압축 1에서만 KB의 API 내 경로 지정 상세 조회·범위 확장을 지원하도록 도구 계약을 확장한다.

top-k·검색 임계값은 UI 옵션에 추가하지 않고 서버 설정으로 관리한다. 조건별 top-k의 초기값은 5로 하고, 허용 범위는 정수 1~10으로 제한한다. top-k는 세 검색 범주 각각에 적용하며, 조건이 여러 개 구조화된 경우 조건 질의별로 적용한다. 관련도 임계값은 초기 0.7이며 LLM 점수의 보정값으로 간주하지 않는다. 후보 STEP 조건은 조건 질의 안에 합치므로 검색 횟수를 별도로 늘리지 않는다. API 내 검색 가능한 필드 수가 k보다 적으면 그 수만 반환한다. 같은 텍스트 질의는 출처를 기록한 채 합치고, 결과는 parameter_path로 중복 제거한다. 질의 출처·관련 STEP 점수와 선정 근거는 retrieval 로그에 남긴다. 정확 일치 후보와 관련 규칙에 필요한 필드는 별도 보존하므로 최종 전달 필드 수는 k를 초과할 수 있다.

구현 후 동일 평가셋에서 k=1~10을 비교해 정답 후보 재현율과 최종 매핑 품질을 유지하는 값을 선택한다. 후보 수만 줄이는 대신 추가 조회가 늘어날 수 있으므로 fallback을 포함한 누적 입력 토큰·총비용·지연도 함께 비교한다. 품질 기준을 만족하는 값 중 누적 입력 토큰이 가장 적은 값을 채택하고, 동률이면 총비용·지연 순으로 판단한다. 채택한 k와 비교 근거를 평가 보고서에 남긴다. 평가 전에는 5를 기본값으로 유지하고, 아직 최적 k가 검증된 것으로 표시하지 않는다. 실제 사용한 k와 검색 임계값은 모델·인덱스 버전과 함께 로그에 기록한다.

유사도 검색은 반드시 데모 내부의 `hyejung/mini_project_2_demo/data/out/parameters/parameter_vectors/`에 복사된 ChromaDB를 사용한다. 경로는 데모 루트 기준으로 계산하고 현재 작업 디렉터리에 의존하지 않는다. `src/tap/retrieval/chroma_index.py`를 재사용하며 기존 컬렉션 `canonical_parameters_cf5a1c85ad4d`, 모델 `text-embedding-3-small`, 기본 1536차원을 기준으로 질의한다. 모델·차원·컬렉션을 먼저 확인하고, 검색 과정에서 다른 모델의 빈 컬렉션을 자동 생성해 기존 인덱스를 사용한 것처럼 처리하지 않는다. 이웃 프로젝트의 벡터 DB를 직접 열거나 새로 전체 임베딩하지 않는다.

데모의 JSON 산출물을 상세 근거 원본으로 삼고, 기존 인덱스와 최신 JSON의 API·파라미터 대응 및 해시 생성 규칙을 먼저 확인한다. 저장된 벡터 레코드 전체를 현재 KB로 간주하지 않고 현재 API·parameter_path에 실제 존재하는 후보만 사용한다. 자료가 변경되면 해시와 임베딩 모델을 대조해 별도 갱신 절차에서 반영한다.

### 4.3 누락·오류와 검증

- 조건별 무검색 결과, 낮은 확신, 경쟁 후보, 검증 오류에 필요한 경로가 미전달된 경우 현재 k에서 최대 10까지 후보 수 확대 → 경로 상세 조회 → 해당 API 전체 KB 순으로 보완한다. 초기 k=5에서는 먼저 k=10으로 확대한다. 평가로 다른 기본 k를 채택해도 확대 상한은 10이며, 같은 범위를 반복 검색하지 않는다. 전체 KB fallback은 유사도 top-k 검색과 별도 단계로 기록한다.
- 벡터 인덱스가 없거나 검색 서비스가 실패하면 전체 KB로 전환해 기존 기능을 유지하고 원인을 로그에 남긴다. 원본 KB의 손상·부재는 기존 자료 오류 정책을 유지한다.
- 인덱스 생성·질의 임베딩의 시간과 토큰을 별도 계측하고 전체 생성 예산에도 반영한다. 생성 전에 만든 인덱스 비용은 준비 비용으로 따로 기록한다. 실패·추가 조회도 예산에서 제외하지 않는다.
- 무한 확대를 막는 유한한 검색 단계와 예산을 둔다. 같은 상세 자료를 반복 반환하지 않는다.
- 원본 문서는 백엔드에 유지한다. 검색 결과의 배열을 재구성해도 원본 source_id·source_pointer를 사용하고, 코드 문자열의 앞자리 0·enum·타입·XML 경로를 보존한다.
- backend가 전체 문서를 갖고 있다는 사실과 모델이 실제로 전달받은 근거를 구분한다. 압축 1에서는 전달한 근거 목록을 관리하고, 모델이 보지 못한 자료를 인용하면 상세 자료 확보 대상으로 처리한다. 이 처리는 후보 자료 확보이며 매핑 검증 범위를 확대하는 수단으로 사용하지 않는다.

## 5. 압축 2: 의존성 기반 JSON 선별

LLM 요약 없이 백엔드 함수가 필요한 항목을 선택한다. 원본 current/previous/following과 검증·조립 상태는 변경하지 않고 모델 입력 뷰만 새로 만든다.

### 5.1 선별 규칙

- 현재 STEP의 업무 조건, API 식별자, 원본 요청과 근거는 유지한다. 구조 안팎에 중복된 의존성 전달은 한 곳으로 정리하고 프롬프트도 함께 조정한다.
- 선행 STEP은 `input_dependencies`의 출처와 모호한 후보를 기준으로 선택한다. STEP 식별자, API 식별자, 필요한 outputs의 이름·경로·타입·content_type·response_key·path_type·row_scope·근거를 보존한다.
- 필요한 출력 필드까지 확정된 관계는 그 정의만 전달한다. 현재처럼 STEP 수준만 확정된 관계는 해당 STEP의 출력 정의 전체를 전달한다. 필드명을 유사도만으로 잘라내지 않는다.
- 출처가 ambiguous이면 candidate_source_step_ids를 보존한다. 의존성 추출이 불완전하면 전체 선행 출력 또는 기존 문맥으로 넓히고 이유를 기록한다.
- 출력이 없는 관련 선행 STEP도 식별자를 남겨 기존 Response Outputs 조회와 앞 STEP 출력 보완을 사용할 수 있게 한다.
- 후속 STEP은 현재 출력의 소비 관계에 필요한 STEP/API 식별자, 관련 조건과 dependency_id·소비 관계를 전달한다. 소비 관계가 불명확하면 관련 후속 조건의 범위를 넓힌다. 중간 STEP을 통한 연결도 누락하지 않도록 관계를 확인한다.

### 5.1.1 STEP 연결 후보 제안 및 검증

`selection_reason`은 승인 자료에 저장된 현재 STEP의 기존 문자열을 사용한다. LLM이 KB 도구 호출 시 이를 새로 작성하거나 연결 검색어로 재구성하지 않는다. 압축 1은 조건(명확한 기존 관계 또는 임계값 이상인 관련 STEP의 조건을 문맥으로 결합)·original_question·현재 STEP의 저장된 selection_reason 세 범주를 각각 top-k=5 검색하고 결과 경로를 중복 제거한다. 검색 결과에 `dependency_link_context`를 덧붙이지 않는다.

STEP 연결은 기존 매핑 지침대로 처리한다. LLM은 입력에 포함된 승인 의존성·선행 출력과 현재 조건, 조회된 ParameterKB를 검토해 기존 `bindings`와 `inputs(source=bind)`를 작성하고, 근거가 모호하면 unresolved를 사용한다. 백엔드는 실제 출력 정의, 현재 API 입력 경로, 타입 호환성을 검사한다. 별도 연결 분석용 LLM 호출이나 연결 전용 검색어 생성은 하지 않는다.

백엔드는 저장 전에 source step/output이 실제 실행 문맥에 있는지, destination parameter_path가 현재 API schema에 존재하는지, 출력·입력 타입이 일치하는지 검증한다. 압축 모드와 중지조건·재시도 모드에 관계없이 이 연결 안전 검사는 적용한다. 출력 정의가 아직 이전 STEP에 없으면 Response Outputs 조회·보완 절차를 먼저 수행한 뒤 검증한다. 불일치하면 오류 피드백으로 매핑 수정을 요청하고 잘못된 Binding을 저장하지 않는다. 애매한 의존성은 기존 ambiguous 후보를 보존하며 백엔드나 LLM이 근거 없이 STEP을 확정하지 않는다.

### 5.2 근거와 재수정

STEP 키는 유지한다. 선별된 출력 배열에는 원본 인덱스에 대응하는 pointer를 명시하고, 검증은 원본 스냅샷과 대조한다. 선별된 배열의 새 인덱스를 원본 근거 위치로 해석하지 않도록 프롬프트와 evidence 해석을 함께 수정한다. 선택된 출력 객체는 정확한 인용이 가능하게 보존한다.

`Runtime.run()`뿐 아니라 `Runtime.repair()`에서도 같은 선별 함수를 사용한다. 앞 STEP 출력 보완·최종 수정 후에는 최신 전체 상태에서 뷰를 다시 만들고, 새 근거를 모델에 전달한다. 반복 수정 때문에 전체 previous가 재주입되거나 예전 출력만 전달되는 것을 막는다. backend 검증·출력 보완용 ToolRegistry는 전체 상태를 유지한다.

## 6. 두 압축과 재시도의 결합 순서

```text
요청 옵션 정규화·고정 → 전체 승인본·자료 로드 → 고정 계획·의존성 구성
  → STEP 모델 입력 작성: 압축 2가 켜져 있으면 문맥 선별
  → KB 기본 조회: 압축 1이 켜져 있으면 API 내 조건별 검색·상세 반환
  → 기존 조건부 Baseline·Response Outputs 조회 → 매핑 후보
  → stop_retry 선택에 따라 기존 검증·수정·중단 정책 적용
  → 전체 상태로 Baseline 비교·출력 보완·IR 조립
  → stop_retry 선택 시 최종 검사 → 저장·미리보기
```

검색 범위 확대와 문맥 보완은 서로의 누락을 해결할 수 있게 한다. 예를 들어 Binding 오류가 선행 출력 때문이면 KB만 재검색하지 않고 관련 선행 출력 뷰를 보완한다. 정책과 검증 한도는 조회나 문맥 갱신으로 초기화하지 않는다.

### 7.1 결정적인 기능·회귀 검사

모의 LLM·검색 결과로 8개 조합을 파라미터화하여 실제 실행 경로를 확인한다. 옵션 파싱만 검사하지 않는다.

- 새 옵션 생략, legacy basic/validated, 부분 객체, 두 형식의 일치·충돌, 잘못된 자료형을 검사한다.
- 자동 생성·재생성, 일반 JSON·NDJSON 경로에서 옵션·실행 정책·저장 기록이 일치하는지 검사한다.
- UI의 독립 선택·모두 해제·전체 선택·기본값 복원·생성 중 잠금·실패 후 복구와 기존 IR 표시를 확인한다.
- 여러 조건 중 한 조건만 검색되지 않는 경우, 동명이인 필드, enum의 0 접두사, VERIFIED 범위, API 간 동일 필드, 빈 조건, 인덱스 부재·오래된 인덱스를 다룬다.
- top-k 기본값 5, 정수 1~10 검증, 세 출처별 적용, 동일 질의 출처 병합, 후보 경로 중복 제거, API 내 필드 수 상한, k=10 이후 fallback을 확인한다. 데모 내부 Chroma 경로·기존 컬렉션·모델·차원이 실제 사용되는지 확인하고 이웃 프로젝트 DB에 의존하지 않는지 검사한다.
- 관련/무관 선행 STEP, 여러 출력 중 일부 선택, ambiguous 의존성, 누락된 출력, 다단계 소비, 원본 pointer 및 수정 후 출력 갱신을 다룬다.
- stop_retry 선택 시 일시 통신 오류 추가 1회와 STEP 수정 1회, 자료 반복 중단, 최종 수정의 한도 공유를 검증한다. 해제 시 기존 basic 경로를 확인한다.
- 압축 조회와 문맥 보완에도 호출·토큰·시간 예산이 유지되는지 확인한다.
- 기존 tests의 모드·초안·XML 미리보기·UI·자료 조회 회귀 검사를 실행하고 필요한 부분만 확장한다.

### 7.2 실제 모델 성능·비용 비교

동일 승인본·자료 버전·모델·예산으로 8개 조합을 실행한다. 단일 실행 편차를 피하려고 각 태스크를 최소 3회 반복하고, 비용은 임베딩·검색 보완을 포함해 집계한다. 생성 결과의 ID·시각·표현 차이 대신 매핑 의미를 비교한다.

태스크셋에는 다중 조건, 반복 API, 선행 출력 Binding, 모호한 출처, 조회 결과 없음, 큰 KB, 기존 문자열 조건 파일을 포함한다. 각 태스크의 정답 필드·값·출력·Binding·유효한 미해결 기준은 실행 전에 고정한다.

| 분류 | 기록 지표 |
|---|---|
| 품질 | 입력 경로·값·코드 정확도, 출력·Binding 정확도, 근거 유효성, 조건 누락, 타당한 미해결 처리 |
| 검색 | k=1~10별 조건별 정답 후보 재현율, 실제 사용 k, 후보 수, 범위 확대·전체 KB 전환 횟수 |
| 실행 궤적 | 도구 사용, 오류·수정·통신 재시도, 성공/실패·중단 원인 |
| 자원 | 입력·출력·캐시·임베딩 토큰, 총비용, 검색/인덱스 준비 비용, 생성 지연 |
| 문맥 | 전체/선별 전후 크기, 보존 STEP·출력 수, 문맥 확대 횟수 |

압축 조합은 같은 stop_retry 값의 비압축 조합과 비교한다. 즉 010/001/011은 000, 110/101/111은 100을 기준으로 한다. 단순 검증 통과를 업무 조건의 완전성으로 취급하지 않고 별도 정답 기준으로 평가한다.

기능 검증 8종과 회귀 검사는 모두 통과해야 한다. 품질은 평가셋의 기준선 성공 항목을 유지하고 새 누락·잘못된 Binding·잘못된 근거가 없어야 한다. 압축 대상으로 삼은 태스크군에서 누적 입력 토큰 감소를 확인한다. fallback 태스크는 절감이 없어도 허용하되 이유를 기록한다. 실제 비용·지연이 증가하면 그 결과도 보고하고 임계값 조정 후 재평가한다. 절감률을 구현 전에 보장하지 않는다.

## 8. 구현 순서와 산출물

1. 현재 basic/validated의 기존 검사를 실행해 기준선을 기록한다. 조건 형식·출처 계약과 비교 태스크셋을 확정한다.
2. 옵션 정규화·legacy 호환·IR 기록을 구현하고 체크박스 UI와 두 생성 경로를 연결한다.
3. 데모 내부의 기존 ChromaDB를 연결하고 압축 1의 API 한정·조건/original_question/selection_reason별 top-k=5 검색·상세 반환·최대 k=10 확대·계측을 구현한다. 평가에서 k=1~10을 비교해 최종 기본값을 선정한다.
4. 명확한 기존 의존성을 우선 활용하고, 없거나 모호한 관계만 같은 첫 KB tool call에서 후보 STEP 관련도를 판정한다. 임계값 이상으로 선택된 조건을 현재 조건 질의에 합치며, selection_reason은 승인 문자열 그대로 유지한다. Binding 입력 경로·출력 존재·타입 검증은 백엔드에 둔다.
4. 압축 2의 의존성 기반 뷰와 원본 pointer 대응을 구현하고 초기·최종 수정 경로에 공통 적용한다.
5. 두 압축과 stop_retry 결합을 검사하고 기존 검증 범위·예산·저장 동작을 확인한다.
6. 8가지 기능 조합·회귀 검사 및 실제 모델 비교를 실행하고 README와 검증 결과 문서를 갱신한다.

산출물은 구현 코드, 조합별 검사, 변경된 UI, 실행 옵션·검색·문맥 선별 로그, 성능·비용 비교 보고서다. 보고서에는 실행한 항목과 미실행 항목을 구분하며 실제 모델 평가 전에는 성능 유지나 토큰 절감을 완료로 표시하지 않는다.
