## 1. 목표와 적용 범위

승인된 API 실행 계획의 STEP 수에 따라 생성 예산을 산정하고, 실행 중 같은 기준으로 제한·기록·표시한다.

- STEP별 LLM 호출의 **기본 예산은 5회**이며, 이를 초과하는 호출은 전체 STEP이 공유하는 공통 예비 2회에서 차감한다. 최초 생성, 자료 재조회 후 생성, 매핑 수정, 최종 IR 검증 후 수정, 통신 재시도를 모두 포함한다.
- 공통 예비 예산과 요청 전체 절대 상한을 적용한다.
- 임베딩 호출은 LLM 호출 횟수에 포함하지 않는다. 임베딩 토큰과 경과 시간은 전체 토큰·시간 한도에 포함한다.
- 계산된 예산과 실제 사용량을 실시간 이벤트, 저장 JSONL, 생성 결과, 최하단 누적 실행 기록 표에서 확인한다.
- `basic`과 `validated`, 압축 옵션의 모든 조합에 예산 정책을 적용한다. 기존 검증 범위·수정 횟수·통신 재시도 허용 정책은 유지한다.
- 실제 업무 API 실행, 금액 상한, 중단 실행 재개 기능은 이번 구현 범위에 포함하지 않는다.

## 3. 확정할 기본 예산

| 항목 | STEP당 기본값 | 공통 예비 | 전체 절대 상한 |
|---|---:|---:|---:|
| LLM 호출 | 5회 | 2회 | 40회 |
| 누적 토큰 | 50,000 | 30,000 | 400,000 |
| 생성 시간 | 60초 | 30초 | 600초 |
| 호출당 최대 출력 | 4,096토큰 | 해당 없음 | STEP 수와 무관 |

`N = len(fixed_plan(approved))`를 생성 시작 시 확정한다. API 선택 결과의 승인된 STEP 수이며 업무 수, 처리 데이터 건수, 모델 호출 수와 구분한다. 수정·재시도 중 N과 예산을 증가시키지 않는다.

```text
요청 LLM 한도 = min(40, 5 × N + 2)
요청 토큰 한도 = min(400000, 50000 × N + 30000)
요청 시간 한도 = min(600, 60 × N + 30)
STEP LLM 기본 예산 = 5
공통 LLM 예비 = 2 (전체 STEP 공유)
호출당 출력 한도 = 4096
```

| STEP 수 | 요청 LLM 한도 | 토큰 한도 | 시간 한도 |
|---:|---:|---:|---:|
| 1 | 7회 | 80,000 | 90초 |
| 4 | 22회 | 230,000 | 270초 |
| 8 | 40회 | 400,000 | 510초 |
| 10 | 40회 | 400,000 | 600초 |

### 3.1 STEP별 기본 5회와 공통 예비 2회의 관계

**각 STEP은 기본 5회를 사용하고, 6번째부터는 전체 STEP이 공유하는 예비 2회에서 호출당 1회씩 차감한다.** 예비분을 한 STEP이 모두 사용하거나 여러 STEP이 나누어 사용할 수 있다. 다른 STEP의 미사용 기본 예산은 이전하지 않는다.

4 STEP의 요청 전체 한도는 `4 × 5 + 2 = 22회`다.

| 사용 상황 | 공통 예비 사용 | 공통 예비 잔여 | 이후 허용 |
|---|---:|---:|---|
| A가 5회 사용 | 0회 | 2회 | A의 6번째 호출에 예비 사용 가능 |
| A가 6회 사용 | 1회 | 1회 | A 또는 다른 STEP의 기본 초과 호출 1회 가능 |
| A가 7회 사용 | 2회 | 0회 | A의 8번째 호출 차단, 나머지 STEP은 각각 기본 5회까지 |
| A·B가 각각 6회 사용 | 2회 | 0회 | A·B의 추가 호출 차단, 나머지 STEP은 각각 기본 5회까지 |

```text
STEP별 기본 사용량 = min(STEP 누적 LLM 호출, 5)
STEP별 예비 사용량 = max(0, STEP 누적 LLM 호출 - 5)
공통 예비 사용량 = 모든 STEP의 예비 사용량 합계
공통 예비 잔여 = 2 - 공통 예비 사용량
전체 사용량 = 모든 STEP의 기본 사용량 합계 + 공통 예비 사용량
```

다음 호출은 요청 전체 호출·토큰·시간 한도가 남아 있고, 해당 STEP의 기본 예산이 남아 있거나 공통 예비가 남아 있을 때만 허용한다. 전체 호출 수가 22회 미만이어도 공통 예비가 소진된 STEP의 기본 초과 호출은 차단한다.

공통 호출 예비의 소진 여부는 전체 호출이 `5N`을 초과했는지가 아니라 **각 STEP의 5회 초과분 합계**로 판단한다. 예를 들어 A만 7회 사용한 시점에는 전체 호출이 7회여도 공통 예비는 이미 소진되었다.

전체 절대 상한 40회는 기본·예비 모두에 우선한다. 8 STEP이면 기본 합계만 40회이지만, 다른 STEP의 기본 예산을 아직 사용하지 않았다면 40회에 도달하기 전에 예비를 사용할 수 있다. 이 경우 뒤 STEP이 기본 5회를 모두 사용하기 전에 전체 상한에 도달할 수 있다. 예비 2회가 항상 추가 보장되는 것으로 표시하지 않는다.

최종 검증 수정도 원래 STEP의 누적 호출 수를 이어서 사용하며 카운터를 초기화하지 않는다. 자료 재조회·매핑 수정·최종 검증 수정·통신 재시도 모두 같은 기본/예비 차감 규칙을 적용한다. 예비분은 특정 단계에 전용으로 잠그지 않으며 기존 수정 횟수·재시도 허용 정책을 우회하지 않는다.

### 3.2 토큰·시간은 전체 공유

STEP당 50,000토큰·60초는 전체 예산 산정 기준이다. STEP마다 해당 양을 강제로 분할하지 않는다. 한 STEP이 80,000토큰을 사용하더라도 요청 전체 한도와 나머지 정지 조건 안이면 허용한다.

공통 토큰·시간 예비분은 전체 공유 풀에 포함한다. 기본 풀 사용량과 예비분 사용량을 표시하되, 최종 검증 단계에만 배타적으로 잠그지 않는다.

```text
기본 풀 = min(전체 절대 상한, STEP 수 × STEP당 예산)
실효 예비분 = 산정된 전체 한도 - 기본 풀
예비분 사용량 = max(0, 전체 사용량 - 기본 풀)
```

이 기본 풀·실효 예비분 계산식은 토큰·시간에 적용한다. 호출 예비는 3.1절처럼 STEP별 초과분으로 집계한다. 토큰·시간은 절대 상한으로 인해 실효 예비분이 설정값보다 작거나 0이 될 수 있다. 로그에는 설정 예비분과 실효 예비분을 구분한다. 시간·토큰의 예비분 사용은 별도 중복 차감이 아니라 공유 풀의 소비 내역이다.

## 4. 호출·사용량 집계 계약

### 4.1 LLM 호출 단위

- 애플리케이션이 `client.responses.create()`를 실제로 시도하기 직전 STEP와 요청의 카운터를 각각 1 증가시킨다. 해당 STEP의 기존 누적 호출이 5회 이상이면 공통 예비도 1회 차감한다. 한도 검사와 기본/예비 차감은 한 번의 작업으로 처리한다.
- 반환 성공·오류·타임아웃에 관계없이 전송 시도로 집계한다. 서버에서 실행되었는지 알 수 없는 실패도 호출 시도로 남긴다.
- 통신 재시도도 매 시도마다 1회 소비한다. SDK 내부 자동 재시도는 끄고 애플리케이션 재시도만 허용한다.
- 전송 전 예산 검사에서 차단된 호출은 소비하지 않는다. 검증·프롬프트 구성 같은 로컬 작업도 소비하지 않는다.
- 응답 수와 실제 호출 시도 수는 별도 기록한다. 응답 토큰을 기록할 때 호출 수를 다시 증가시키지 않는다.
- 임베딩, 도구, 백엔드 validation은 LLM 호출 횟수에서 제외한다.

### 4.2 토큰과 시간

- 전체 토큰 = LLM 입력 + LLM 출력 + 임베딩 토큰. 캐시 입력은 입력 토큰의 부분집합이므로 다시 더하지 않는다.
- 응답이 없는 통신 오류는 토큰을 0으로 확정하지 않는다. 확인된 사용량과 `usage_unknown_attempts`를 구분한다.
- 요청 시간은 예산 확정 후 Runtime 실행 시작부터 최종 검증·저장 완료까지 단일 monotonic 시계로 측정한다. 로그 파일 생성부터의 기록 시간은 별도 필드로 유지한다.
- 자료 조회, 임베딩, 백엔드 처리, 재시도 대기 시간을 포함한다. STEP 변경·수정 시 시계를 초기화하지 않는다.
- 임베딩 횟수·토큰·시간을 별도 집계하며, 토큰·시간 검사도 임베딩 전후 수행한다.

### 4.3 호출 전 토큰 확인과 정지

다음 입력에는 instructions, tools, 출력 스키마, 메시지, 이전 응답 등을 포함해 입력량을 추정한다. 모델에 맞는 추정과 보수적 여유분을 사용하고, 실제 응답 사용량으로 정산한다.

```text
허용 출력 = min(4096, 남은 토큰 - 예상 입력 - 추정 여유분)
```

허용 출력이 API가 요구하는 최소 출력량에 못 미치면 전송 전에 중단한다. 입력량 추정은 정확한 과금 토큰 보장이 아니므로, 사후 초과 검사와 초과량 기록도 유지한다. 임베딩 입력에도 사전 추정 검사를 적용한다.

LLM·임베딩 timeout은 남은 전체 시간 이내로 설정한다. 도구 배치의 각 실행 전, 최종 검증·저장 전후에도 시간을 확인한다. 비중단형 로컬 작업은 완료 후 초과를 감지할 수 있음을 문서화한다.

## 5. 설정·API·결과 구조

### 5.1 정책과 산정 결과 분리

`src/tap/agent/budget.py`를 추가해 정책 검증, 산정, 사용량 스냅샷, 제한 확인을 모은다. 산정 결과와 카운터를 Runtime·UI·로그에서 각각 재계산하지 않는다.

정책 필드 초안:

```json
{
  "version": "step_budget_v1",
  "per_step": {"llm_calls": 5, "tokens": 50000, "seconds": 60},
  "reserve": {"llm_calls": 2, "tokens": 30000, "seconds": 30},
  "absolute": {"llm_calls": 40, "tokens": 400000, "seconds": 600},
  "max_output_tokens": 4096
}
```

서버가 모든 예산 정책을 소유한다. STEP별 기본 호출 5회, STEP당 토큰·시간, 공통 예비분, 절대 상한, 호출당 출력 한도는 모두 화면에서 수정할 수 없다. 기본 초과 호출은 공통 예비 2회에서 허용한다. 정책값 변경은 서버 설정에서만 수행하고 정수 여부, 양수·음수, 알 수 없는 키를 검사한다.

신규 화면의 미리보기·생성 요청은 승인본 식별자와 생성 옵션만 전달하고 예산 숫자는 전송하지 않는다. 서버가 `budget_policy`를 구성하고 승인본 STEP 수로 산정한다. 기존 숫자 `config`를 명시한 호출은 `legacy_fixed_v1` 경로로 구분해 종전 계약을 유지한다. 기존 config 경로는 호환용으로만 남기며 화면에서는 사용하지 않는다. 신규 STEP 예산 요청에 클라이언트가 예산 정책이나 산정 한도를 덮어쓰려 하면 거절한다. config를 생략한 요청은 새 STEP 예산 정책을 적용한다. 기존 화면은 신규 형식으로 전환한다. legacy 실행도 임베딩 제외 등 새로운 호출 집계 정의를 사용하고 버전으로 의미를 명시한다.

### 5.2 예산 스냅샷

`budget`에는 버전, STEP 수, 정책, 상한 적용 전 산정값, 실효 한도, 토큰·시간 기본 풀과 실효 예비분, 호출 공통 예비 2회, 상한 적용 여부를 저장한다. `budget_usage`에는 전체·STEP별 실제 호출 시도, 응답 수, 토큰, 시간, 임베딩, 예비분 소비를 저장한다. 호출은 STEP별 기본/예비 사용량과 전체 예비 사용/잔여를 따로 저장한다. 호출 예비는 전체 사용량에서 기본 풀을 빼서 계산하지 않는다.

저장 IR의 `generation.budget`과 생성 API 결과에도 같은 스냅샷을 포함한다. 기존 `generation.config`의 4개 숫자와 기존 usage 필드는 호환용으로 유지하고 의미를 README에 명시한다. 내부 `max_turns`를 유지할 경우 새 정책에서는 임베딩을 제외한 전체 LLM 시도 상한으로 매핑한다.

## 6. 실행 흐름과 JSONL

```text
요청 수신·journal 시작
→ 승인본 검증·fixed_plan 확정
→ STEP 수 기반 예산 산정·스냅샷 고정
→ budget_initialized 기록
→ STEP 실행: 각 전송 시도 전 검사·차감 → 응답 사용량 정산
→ 필요 시 최종 IR 검증·수정: 원 STEP 카운터와 같은 예산 사용
→ 시간 확인·초안 저장 → 최종 예산 사용량 기록
```

- `generation_start`는 입력 요청을 기록한다. 계획이 아직 없는 단계에 산정값을 추측해 넣지 않는다.
- `budget_initialized`는 LLM·임베딩 호출 전에 확정 예산을 기록한다.
- 전송 시도 시작, 응답, 임베딩 결과, STEP 완료, 검증 수정, 최종 성공·실패에 `budget` 또는 이를 참조할 버전과 `budget_usage`를 포함한다. 실패 직전에도 journal이 최신 카운터를 보관한다.
- `budget_exceeded`에 `reason_code`, `scope`, `step_id`, `phase`, `used`, `limit`, 차단된 작업을 기록한다. 예상 입력 부족과 실제 토큰 초과를 구분한다.
- 사유 코드는 `STEP_LLM_RESERVE_EXHAUSTED`, `RUN_LLM_LIMIT`, `RUN_TOKEN_LIMIT`, `RUN_TIME_LIMIT`, `INSUFFICIENT_REQUEST_TOKENS` 등으로 고정한다.
- 실패 응답·최종 `generation_error`에도 마지막 예산·사용량·사유를 넣어 하단 표에서 확인한다. 한도 중단 사유가 일반 실패 이벤트에 가려지지 않게 한다.
- 계획 검증 실패 등 예산 산정 전 실패는 `budget: null`로 남긴다.
- 기존 이벤트의 순서·run_id·마스킹·flush·다운로드 동작을 유지한다.

## 7. 화면과 실행 기록 요약 API

### 7.1 생성 설정과 진행 상태

기존 예산 수정 UI를 **읽기 전용 STEP 기반 예산 표시**로 전환한다. 모든 예산값은 사용자가 수정할 수 없다. STEP별 기본 호출 5회와 기본 초과 시 공유하는 예비 2회, STEP당 토큰·시간, 절대 상한, 호출당 출력 한도 및 산정된 전체 예산을 표시한다. 숫자 입력과 예산 ‘기본값으로 복원’ 버튼은 제거하고 텍스트 또는 읽기 전용 표로 보여준다.

- STEP 문서(저장된 승인본)를 처음 로드하거나 다른 문서로 변경하면 서버가 `fixed_plan()`으로 STEP 수를 확인해 해당 문서의 예산을 즉시 자동 산정·표시한다. 생성 버튼을 누르기 전에도 확인할 수 있어야 한다.
- 예: 4 STEP 문서 로드 시 `STEP 4개 · LLM 22회 · 토큰 230,000 · 시간 270초 · 호출당 출력 4,096`을 표시한다.
- 문서를 바꾸면 이전 문서의 예산을 지우고 로딩 상태를 표시한다. 빠르게 문서를 변경했을 때 늦게 도착한 이전 응답이 현재 값을 덮어쓰지 않도록 문서 ID 또는 요청 순번을 확인한다.
- 문서 미선택·로드 실패·승인 계획 검증 실패 시 한도를 추측하지 않고 `문서 로드 필요` 또는 오류를 표시하며 생성 실행을 막는다.
- 실제 생성 시 서버가 문서를 다시 읽고 같은 산정 함수로 예산을 확정한다. 문서 내용이 달라졌다면 확정 STEP 수·예산을 화면에 갱신하고 이번 실행 스냅샷을 기준으로 사용한다.
- 실행 중 표시하는 예산은 실행 시작 시 확정된 값으로 유지한다. 문서 선택 변경은 잠그고, 종료 후 다른 문서를 로드하면 새 예산을 표시한다. 생성 옵션 선택 기능은 유지한다.

진행 상태에는 현재 STEP 호출 `3 / 기본 5` 또는 `6 (기본 5 + 예비 1)`, 공통 호출 예비 `1 / 2 사용`, 전체 LLM 호출 `9 / 22`, 토큰 `94,929 / 230,000`, 경과 시간 `103 / 270초`, 임베딩 호출 `4회`를 표시한다. 임베딩 호출에는 LLM 한도 분모를 붙이지 않는다.

### 7.2 최하단 ‘누적 IR 실행 기록’ 표

기존 표를 다음처럼 확장한다. 숫자는 천 단위 구분을 사용한다.

| 컬럼 | 표시 예시 |
|---|---|
| STEP 수 — 추가 | `4` |
| 수행 시간 — 사용량/한도 | `103초 / 270초` |
| 모델 호출 → LLM 호출 — 사용량/한도 | `9 / 22` |
| STEP 최대 호출 — 추가 | `6 (기본 5 + 예비 1)` |
| 임베딩 호출 — 추가 | `4회` |
| 총 토큰 — 사용량/한도 | `94,929 / 230,000` |
| 예비 사용 — 추가 | `호출 0/2 · 토큰 0/30,000 · 시간 0/30초` |
| 중단 사유 — 추가 | `STEP 2-2 기본 5회 소진·공통 예비 2/2 소진` 또는 `—` |

실행 시각·생성 옵션·상태·턴·입력/출력/임베딩 토큰·JSONL 링크는 유지한다. 열이 많아지면 기존 가로 스크롤을 사용한다. 행 상세 또는 설명에 전체 예산 산정식, 절대 상한 적용 여부, STEP별 호출 사용량과 예비분 제약을 표시한다.

### 7.3 과거 로그 호환

`scenario_ir_log_summaries()`가 새 `budget`과 `budget_usage`를 우선 읽도록 한다. 과거 로그의 명시된 설정은 ‘고정 예산’으로 표시하고, 한도가 없으면 `사용량 / —`로 표시한다. 현재 기본값으로 과거 한도를 추측하지 않는다.

새 로그에서는 실제 시도 카운터를 직접 사용하고 기존 `max(attempt_count, request_count)` 추정은 과거 로그에만 적용한다. 임베딩이 없는 과거 로그는 기록 여부에 따라 0 또는 `—`로 구분한다. 손상된 일부 JSONL 행과 최종 이벤트가 없는 실행도 기존처럼 조회할 수 있게 한다.

## 8. 구현 순서와 산출물

1. `config.py`와 신규 `budget.py`: 정책 모델, 계산식, 절대 상한, STEP 기본 5회와 공유 예비 2회 차감, 버전 및 호환 계약 구현.
2. `draft_build.py`: 승인 계획을 한 번 확정하고 예산 산정·이벤트·Runtime·IR 결과에 동일 스냅샷 전달. 설정 재적용 시 예산이 초기화되지 않게 한다.
3. `runtime.py`, `llm_retry.py`, `kb_retrieval.py`: 실제 시도 카운터, SDK 재시도 제거, 호출 전·후 한도 검사, STEP별 누적·수정 연계, 임베딩 분리.
4. `logging.py`, `progress.py`: 예산·사용량·사유 스냅샷과 최종 실패 보존.
5. `serve.py`: 서버 고정 정책·승인본 로드 시 예산 조회·실행 요청 계약 및 로그 요약 확장.
6. `scenario-ir-draft.js` 및 필요 시 기존 CSS: 예산 수정 UI 제거·문서 로드 시 읽기 전용 예산 갱신·진행 상태·하단 표의 사용량/한도 표시.
7. 예산 테스트 추가와 기존 회귀 테스트 실행. README에 계산식, 호출 정의, 상한·예비분의 제약, 과거 로그 표시를 반영.

## 9. 검증 계획과 완료 조건

| 검증 영역 | 필수 확인 |
|---|---|
| 산정 | 1·4·8·10 STEP 계산값, 절대 상한 적용, 잘못된 정책 입력 거절 |
| STEP 기본·예비 | A의 6번째·7번째 호출이 예비를 각각 1회 소비하고 8번째 차단, 다른 STEP은 기본 5회 사용 가능 |
| 예비 공유 | A·B가 각각 6회면 예비 2회 소진, 전체 호출이 `5N` 미만이어도 기본 초과 호출 차단, 미사용 기본 예산 이전 금지 |
| 전체 호출 | 4 STEP 합계 최대 22회, 40회 이후 예비가 남아도 차단, 8 STEP에서 예비 선사용 후 기본 예산 보장 불가 확인 |
| 재시도 | 실패 전송도 1회 집계, 남은 기본·예비·전체 허용량이 1회일 때 첫 실패 후 재시도 차단, SDK 숨은 재시도 없음 |
| 임베딩 | 임베딩을 여러 번 해도 LLM 호출 불변, 토큰·시간은 누적 반영 |
| 공유 풀 | 한 STEP이 5만 토큰을 넘어도 전체 잔여가 있으면 진행, 실효 예비분 정확히 표시 |
| 사전 검사 | 예상 입력·출력 공간 부족 시 전송 차단, 사후 실제 초과도 사용량 보존 |
| 시간 | 재시도 대기·임베딩·최종 검증 시간 포함, 가짜 시계로 경계 검사 |
| 상태 보존 | STEP 수정·옵션 적용·최종 재조립이 카운터를 초기화하지 않음 |
| 실패 로그 | 응답 없는 실패·예산 중단·산정 전 실패·부분 로그를 정확히 요약 |
| 화면 | 새·과거 로그, 예산 미상, 절대 상한 적용, 실패 행에 사용량/한도 표시 |
| 문서 로드·읽기 전용 | 최초 로드·문서 변경 시 STEP 수에 맞는 예산 자동 표시, 늦은 응답 무시, 로드 실패 처리, 모든 예산 편집·복원 UI 제거, 클라이언트 예산 덮어쓰기 거절 |
| 회귀 | 기존 모드·압축·XML 미리보기·다운로드·옵션 필터·legacy 요청 유지 |

모의 client와 가짜 시계를 사용하는 예산 테스트를 추가한다. 기존 `test_scenario_ir_drafts.py`, `test_scenario_ir_modes.py`, `test_context_compression.py`, `test_scenario_ir_ui.py`, `test_scenario_ir_xml_preview.py` 중 영향받는 검사와 관련 UI 테스트를 실행한다. 계획서 작성 단계에서는 제품 테스트나 유료 API 호출을 실행하지 않는다.

완료 기준은 화면·JSONL·요약 API·저장 결과의 한도와 사용량이 일치하고, STEP별 기본 5회 초과분이 공유 예비 2회에서 정확히 차감되고, 기본 예산과 공통 예비가 모두 소진된 STEP의 추가 호출 및 요청 절대 상한 이후의 호출이 실제 전송 전에 차단되는 것이다. 로그만 보고 산정 근거·호출 정의·중단 원인을 재구성할 수 있어야 한다.

구현 후 STEP 수와 난이도가 다른 고정 태스크셋으로 고정 예산 대비 완료율·검증 통과율·예산 중단율·호출·토큰·지연을 비교한다. 성공·실패 비용을 함께 집계하고 모델·옵션·태스크를 고정한다. 실제 금액은 모델별 단가와 캐시 입력·출력·임베딩 사용량으로 별도 산출하며, 단순 토큰 합을 비용으로 표시하지 않는다.
