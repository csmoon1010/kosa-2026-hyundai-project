# Adaptive RAG 그래프 구현 작업계획서

## 1. 목적과 현재 범위

`day05/mini_project_1/mini_project_final.ipynb`의 「4단계. Adaptive RAG (라우팅) 적용」에서 질문 유형에 따라 하나의 검색 경로를 선택한다. 기존 저장소·공통 답변 프롬프트·K=6·BASE 및 Adaptive 평가 셀과 저장된 결과를 보존한다.

혼합 분류, 병렬 검색, 별도 근거 결합·충분성 판단 LLM, 부족 근거에 따른 BASE 추가 검색, 혼합 전용 답변 프롬프트와 9,000자 제한의 구현·적용 계획은 폐기한다. 기존 세 경로를 유지한다. 이번 변경은 분류 프롬프트 개선에 한정하며, 조건과 부정/예외를 각각 답해야 하는 질문은 정상 기본 분류로 BASE를 선택한다. 검색 설정·그래프·답변 프롬프트는 변경하지 않고 평가나 유료 모델 호출도 실행하지 않는다.

## 2. 서비스 경로와 설정

| 분류 | 서비스 표시 이름 | 그래프 노드 | 검색 동작 |
|---|---|---|---|
| 기본 | 기본 벡터 검색 | `base_search` | 기존 BASE 컬렉션에서 최대 6개 검색 |
| 조건 | Parent Document 검색 | `parent_document_search` | 자식 청크로 검색한 뒤 부모 문서를 최대 6개 반환 |
| 부정/예외 | LLM 리랭킹 검색 | `llm_rerank_search` | BASE 후보 최대 12개를 리랭킹하여 최대 6개 반환 |

부모 청크 크기=1500/중첩=0, 자식 청크 크기=450/중첩=75, 분류 확신도 임계값=0.8을 유지한다. 실험 식별자 R1/S1은 초기 정책 연결에서만 변환한다. 최종 답변은 모든 경로에서 기존 공통 프롬프트로 한 번 생성한다.

## 3. 질문 분류와 그래프

원질문만 분류기에 전달한다. 검색 문서·골든 유형·골든 정답은 제공하지 않는다. `AdaptiveRoute`는 `route_type: Literal['기본','조건','부정/예외']`, 0~1 `confidence`, 한 문장 `reason`을 반환한다. 분류 프롬프트는 `"""` 여러 줄 문자열로 유지한다.

조건은 필수자료·자격·충족 기준, 부정/예외는 허용·금지·제외·면제 판단, 기본은 일반 사실·금액·기한·목록·절차 등을 처리한다. 필수자료·충족 기준과 금지·제외·예외 판단을 각각 답해야 하면 기본을 우선 선택한다. 필요한 행동 하나만 묻거나 예외 적용 조건만 묻는 질문과 구분한다. 자기보고 확신도는 검증된 정확도 확률로 취급하지 않는다.

### 3.1 두 유형 동시 요구의 BASE 선택 규칙

- 조건과 부정/예외의 독립적인 요구사항을 모두 답해야 하면 `route_type='기본'`으로 분류한다. 주된 의도로 한 요구를 버리지 않는다.
- 정상 BASE 선택이므로 확신도를 의도적으로 낮추거나 오류 복귀로 취급하지 않는다. 확신도가 임계값 이상이면 `selected_route='base_search'`, `fallback=False`이며, 이유에는 두 요구를 함께 처리하는 목적을 남긴다. 실제 불확실성·분류 실패는 기존 복귀 규칙을 따른다.
- 필요한 행동·자료 하나를 부정형으로 묻는 질문은 조건이다. 예외 적용 조건만 묻는 질문은 부정/예외다. 부정 표현이나 '조건·경우·기준'이라는 단어만으로 동시 요구라고 판단하지 않는다.
- 별도의 유사 예시로 경계를 설명하며 평가 문항을 그대로 예시에 넣지 않는다. 분류기의 입력에는 골든 유형·정답이나 검색 근거를 포함하지 않는다.

| 질문 예시 | 분류 | 이유 |
|---|---|---|
| 접수 제한을 피하려면 어떤 동의가 필요한가요? | 조건 | 필요한 행동 하나 |
| 정기검사 면제를 받는 조건은 무엇인가요? | 부정/예외 | 예외 적용 조건만 요구 |
| 인증 표시에 필요한 서류와 표시가 금지되는 경우를 각각 알려주세요. | 기본 | 필수자료와 금지 판단을 각각 요구 |

상태는 `question`, `route_type`, `confidence`, `classification_reason`, `selected_route`, `fallback`, `fallback_reason`, `docs`, `answer`를 갖는다. 분류 유형과 실제 실행 경로는 별도로 기록한다.

```text
START → classify_question
          ├─ 조건·확신도 충족 → parent_document_search
          ├─ 부정/예외·확신도 충족 → llm_rerank_search
          └─ 기본·불확실·분류 실패 → base_search
       → generate_answer → END
```

특수 검색 오류 또는 빈 결과 시 BASE를 한 번 실행하고 복귀 이유를 기록한다. BASE 실패는 호출자에게 전달한다. 검색 결과가 있다는 이유만으로 충분한 근거가 확보됐다고 주장하지 않는다. 근거 충분성을 판정하는 별도 LLM·추가 검색 루프는 두지 않는다.

## 4. Parent Document 저장소 구성

### 4.1 현재 실험 구현

- `header_docs`에서 부모 청크를 1500자로 나눈다.
- 각 부모를 450자/중첩 75자의 자식 청크로 나눈다.
- 자식 metadata에 부모 리스트 위치를 나타내는 정수 `parent_id`를 기록한다.
- 자식만 `retrieval_children` Chroma 컬렉션에 임베딩한다. 현재 수정된 소스는 BASE와 같은 `persist_directory=CHROMA_PATH`를 지정하며, 동일 내용·metadata·임베딩 모델의 인덱스를 재사용한다. 변경 시 `rebuild=True`로 명시적인 재구축이 필요하다.
- 부모는 Chroma에 저장하지 않고 Python `parents` 리스트에 보관한다.
- 자식 검색 결과 최대 K×2개에서 부모 ID를 중복 제거하고 부모 청크 최대 K개를 답변 근거로 반환한다.

따라서 현재 구조는 BASE와 같은 영속 경로의 별도 자식 컬렉션을 사용하지만, 부모·자식을 각각 Chroma에 저장한 구조는 아니다. 노트북 재실행을 전제로 한 구성이다.

### 4.2 서비스 구현 방향

작은 청크를 검색하고 큰 부모 문맥을 반환하는 구조는 유지하되 저장과 로딩을 서비스용으로 분리한다.

- 자식은 BASE와 구분되는 영속 Chroma 컬렉션 `parent_document_children`에 저장한다. 같은 영속 DB 디렉터리에 별도 컬렉션을 사용하는 방식도 가능하며 별도 서버·DB가 필수는 아니다.
- 부모는 영속 docstore에 `parent_id → Document`로 저장한다. 현재 로컬 프로젝트의 기본안은 LangChain의 파일 기반 저장소와 Document 직렬화 어댑터를 사용한다. 실제 import는 설치된 버전에서 확인한다.
- 정수 리스트 위치 대신 문서 출처·페이지·절·내용을 바탕으로 안정적인 부모 ID를 부여한다. 자식의 부모 ID와 docstore 키를 일치시킨다.
- source·page·헤더 등의 출처 metadata를 부모와 자식에 유지한다.
- 인덱스 구축은 별도 준비 셀에서 명시적으로 수행한다. 질의 처리마다 `reset_collection()`이나 재임베딩을 호출하지 않는다.
- 저장된 자식 인덱스가 있으면 자동 로딩하고 없으면 최초 구축한다. prepare_adaptive_resources는 rebuild만 인자로 받는다. 설정 불일치·부모 누락은 자동 재구축하지 않으며 rebuild=True를 요구한다. 원문 변경 시에도 명시적으로 재구축한다.
- 부모 ID가 없거나 조회에 실패하면 원인을 기록하고 기본 검색으로 복귀한다. 조회 성공 시 검색 순서를 보존하고 중복 부모를 제거한다.

대규모·다중 서버 운영의 저장소 선택은 이번 노트북 그래프 구현 범위에 포함하지 않는다. 현재 제안은 로컬 앱에서 프로세스 재시작 후에도 동일 인덱스를 로드할 수 있는 구성이다.

## 5. 이번 변경과 실행 순서

이번 변경은 노트북의 `ADAPTIVE_CLASSIFICATION_PROMPT`만 수정한다. 분류 스키마, 그래프, 검색기, K, 답변 프롬프트, 평가 함수 및 저장된 출력은 유지한다. 프롬프트는 `"""` 여러 줄 문자열로 작성한다.

공통 체인 정의 → 그래프 준비 → 비교 준비 순서로 다시 실행한다. 커널이 초기화되었거나 과거 혼합 정의가 남아 있다면 서비스 설정 → 저장소 함수 → 공통 체인 → 그래프 함수 → 그래프 준비 → 평가 함수 정의 → 비교 준비 순서로 실행한다. BASE 결과를 재사용할 때 BASE 설정 셀은 다시 실행하지 않는다. 실제 품질 비교가 필요하면 이후 Adaptive 평가 → 결과 비교를 실행한다.

기존 구성 서명에 분류 프롬프트가 포함되므로 변경 전 Adaptive 평가를 새 프롬프트 결과로 재사용하지 않는다. 저장된 출력은 변경 전 결과이며 실제 라우팅은 재실행 후 확인한다.

## 6. 후속 검증 및 추가 보완 후보

- **이번 프롬프트 변경 검증:** `original-16`이 기본으로 분류되는지, 선택 이유와 실제 BASE 경로가 일치하는지 확인한다. 순수 조건·순수 예외·동시 요구·부정 표현만 있는 질문을 새로운 사례로 비교한다. BASE가 정답 근거를 회수하는지와 업무 위험도까지 확인하며 BASE 선택 자체를 품질 개선으로 간주하지 않는다.
- **유형 라벨과 검색 경로 평가 분리:** 골든 유형 불일치만으로 오분류를 확정하지 않는다. 질문 유형은 데이터셋의 분류 기준으로 검토하고, 경로 적합성은 실제 근거 회수와 답변 품질로 검증한다.
- **기존 검색 설정 조정:** Parent 검색의 자식 후보 수, 부모 청크 크기·중첩, BASE 리랭킹 후보 수를 한 번에 하나씩 조정한다. 별도 LLM 판단이나 복수 경로 결합은 추가하지 않는다.
- **원문·골든 정답 대조:** `original-16`의 제출자료·균주·금지 기준이 원문에 존재하는지, 청킹·인덱스에서 누락됐는지 확인한다. 성능을 높이려는 목적으로 정답을 바꾸지 않는다.

분류 프롬프트 수정과 검색 설정 변경을 동시에 하지 않는다. 동일 조건에서 변경 전후의 경로·핵심 근거 회수·관련성·재현율·업무 위험·비용·지연을 비교하고 새로운 사례와 반복 실행으로 검증한다. 전체 평균 상승만으로 정책을 확정하지 않는다.
